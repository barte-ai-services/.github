Cada organização tem um repositório, `barte-ai-platform-<slug>`, com a instalação e todos os seus projetos. Ele nasce do template [`barte-ai-platform`](https://github.com/barte-ai-services/barte-ai-platform). Cada módulo da plataforma tem o seu repositório, com uma forma comum. O caminho de uma mudança até production está em [do commit à produção](/how-we-work/delivery).

## O repositório da organização

A árvore é a do template. O que é da instalação fica na raiz; o que é de cada projeto fica em `projects/<project-slug>/`.

```text
barte-ai-platform-<slug>/
├─ .forge/ .claude/ .codex/     o Barte Forge, o Claude Code e o Codex
├─ AGENTS.md CLAUDE.md          as regras para agentes; o CLAUDE.md importa o AGENTS.md
├─ README.md LICENSE            o que é, e a licença
├─ versions.tf                  a versão fixada de cada módulo
├─ Makefile .env.example        os alvos de sempre, e toda variável que a subida lê, sem valor real
├─ component-map.yaml           o mapa dos componentes do repositório
├─ api/                         o contrato platform.openapi.json da instalação
├─ infra/
│  ├─ github/                   os nomes das variables do GitHub Actions, sem valor
│  ├─ scripts/                  os scripts da instalação
│  └─ aws/
│     ├─ bootstrap/             o acesso ao deploy na conta
│     └─ terraform/             a instalação: rede, base e um deployment de cada módulo
│        ├─ modules/ tests/
│        └─ environments/{staging, production, local}/
├─ connectors/                  os conectores do Integration Gateway, e os packs do Data Operator
├─ brand/                       a marca que as telas usam
├─ shell/                       o menu e as telas do Shell
├─ packages/                    config · secrets · observability, e o que os projetos compartilham
├─ projects/
│  └─ <project-slug>/           um projeto, uma linha de operação; podem ser vários
│     ├─ project.yml            o identificador e o slug do projeto
│     ├─ apps/                  os serviços que atendem, um por pasta
│     ├─ workers/               os processos que trabalham, um por pasta
│     ├─ packages/              as bibliotecas do projeto, uma por propósito
│     ├─ flows/                 os fluxos do Workflow Manager
│     ├─ views/                 as visões do Data Operator: a pergunta que a instalação aceita responder
│     ├─ dashboards/            as telas de dashboard, sobre as views
│     ├─ agents/                os agentes do Guild em uso, e os do projeto
│     ├─ tests/{contract, integration, e2e, pentest, stress, fixtures}/
│     ├─ docs/                  a documentação do projeto
│     └─ deploy/
│        ├─ compose/            sobe o projeto local, com os módulos em contêiner
│        └─ aws/terraform/environments/{staging, production, local}/
│                               só os apps e workers do projeto, dentro da instalação
└─ .github/{CODEOWNERS, ISSUE_TEMPLATE/, workflows/}
```

`environments/local/` é a subida no emulador, na máquina de quem desenvolve. Os ambientes de conta são só `staging` e `production` ([nomes](/how-we-work/naming)).

| Regra | O que diz |
|---|---|
| Uma instalação por ambiente | O `infra/aws/terraform` da raiz sobe a rede, a base e os módulos, nas versões do `versions.tf`. Todos os projetos usam essa instalação. |
| O projeto sobe só o que é dele | O `deploy/aws/terraform` do projeto implanta os apps e workers dele. Os fluxos rodam no Workflow Manager, o dado passa pelo Data Operator e o login é o Identity Manager. |
| Um Integration Gateway para todos | Os conectores de todos os projetos ficam em `connectors/`. O Integration Gateway é a única saída da conta. |
| O projeto é autocontido | Um projeto não importa outro, só o `packages/` da raiz. |
| O nome do artefato é único | O nome de cada app e worker é único no repositório, entre todos os projetos, e vira uma imagem própria. |
| O canônico | As views leem o modelo canônico que o Data Operator gera a partir de cada modelo de dados que entra ([dados](/specifications/data)). |

## O repositório de um módulo

Os módulos são o Integration Gateway, o Data Operator, o Workflow Manager, o Identity Manager, o Shell e o Guild. Todos têm a mesma forma.

```text
<module>/
├─ AGENTS.md CLAUDE.md README.md LICENSE CHANGELOG.md VERSION
├─ Makefile                     help · up · down · logs · check
├─ apps/<name>/                 um serviço que atende: HTTP, MCP, a API das telas
├─ workers/<name>/              um processo que trabalha: fila, agenda, task queue
├─ packages/<name>/             uma biblioteca, um propósito só
├─ tests/                       o que atravessa o módulo
├─ docs/                        a documentação, na árvore abaixo
└─ deploy/
   ├─ compose/compose.yml       sobe local
   └─ terraform/aws/            o módulo que a instalação consome
```

| Regra | O que diz |
|---|---|
| `make check` é o CI | O alvo `check` roda o mesmo que o `ci`. O que passa local passa no PR. |
| A dependência desce | `apps/` e `workers/` importam `packages/`, e um não importa o outro. Pacote nunca importa deployável. |
| Três pacotes em todo componente | `config` valida a configuração na subida, `secrets` lê as credenciais do cofre e `observability` exporta log, traces e métricas por OpenTelemetry. |
| Um pacote, um propósito | O nome diz o que ele faz. Nunca `utils` nem `common`. |
| O teste fica junto | Cada app, worker e pacote tem o seu `test/`. |
| Cada deployável é uma imagem | Cada pasta de `apps/` e `workers/` vira uma imagem, atestada. |
| A versão é a tag | A versão do módulo é a tag; um pacote não é publicado à parte. |

| Linguagem | Workspace | Ferramentas |
|---|---|---|
| TypeScript | pnpm, em `pnpm-workspace.yaml` | Node 24, ESLint, Prettier, vitest e `tsc` |
| Python | uv, em `[tool.uv.workspace]` | Python 3.12 ou mais novo, ruff, mypy e pytest |

O detalhe das ferramentas e da cobertura está em [ferramentas](/specifications/tooling).

## O acesso a modelo

Todo acesso a modelo de IA passa pelo AI gateway do Guild (LiteLLM, em `guild/deploy/ai-gateway`, com os módulos Terraform `model-access` e `ai-gateway`), com o Bedrock como provedor atrás. Um lugar só controla os modelos, o custo e as chaves. Nenhum código chama o `bedrock-runtime` direto, e o laço de um agente é um workflow do Workflow Manager.

## O README

Todo README segue esta ordem:

| Seção | Responde |
|---|---|
| Abertura | O que o repositório é, onde termina e a stack. |
| Estado | O que existe e o que falta. |
| Subir | O comando que sobe local, e o que sobe junto. |
| Configuração | As variáveis que a subida lê, com o padrão de cada uma. |
| Layout | A árvore, uma linha por diretório. |
| Entrega | Como sai uma versão, e onde o artefato é publicado. |
| Fronteiras | De quem depende e quem depende dele, com link para cada repositório. |
| Licença | Uma linha, com link para o `LICENSE`. |

O README aponta para a documentação sem repetir o conteúdo.

## A árvore `docs/`

| Pasta | Responde |
|---|---|
| `agents/` | O que um agente de IA lê: as ferramentas MCP, as skills e o que ele recusa. |
| `architecture/` | Como o repositório é construído, e por quê. Os ADRs ficam em `architecture/decisions/`. |
| `domain/` | Os objetos de negócio, os vínculos e os termos. |
| `operations/` | Como operar: alertas, falhas e runbooks, a partir de `operations/README.md`. |
| `reference/` | A interface exposta: rotas, schema, ferramentas e eventos. |
| `security/` | Os dados, quem os acessa, a guarda da credencial e o que nunca sai. |
| `workflows/` | Os processos, do gatilho ao resultado. |

Todo repositório mantém também o `docs/decisions.md`, o índice das decisões. O formato dos ADRs e o site estão em [documentação](/how-we-work/documentation).

## Os agentes de desenvolvimento

| Pasta | Guarda |
|---|---|
| `.forge/` | O Barte Forge: as regras, as skills e os plugins do time. |
| `.claude/` | O Claude Code: `settings.json`, skills, agentes e comandos. |
| `.codex/` | A configuração do Codex. |

A regra do repositório fica no `AGENTS.md`, ao lado do [bloco do handbook](/how-we-work/agents). A configuração pessoal, como `.claude/settings.local.json`, entra no `.gitignore`, e nenhuma das três pastas guarda credencial.

## A licença

Todo repositório tem na raiz o `LICENSE` canônico da organização: proprietário, todos os direitos reservados. Ninguém o escreve à mão: o workflow reutilizável `license-sync` do `.github` copia o arquivo da organização para o repositório.
