Nenhuma mudança começa sem uma issue, e nenhuma construção começa sem um plano aprovado. Quem encontra trabalho sem issue abre uma antes do pull request.

## O que uma issue carrega

- **Por que**: o que está errado ou faltando, com a evidência.
- **Como fica o pronto**: os critérios de aceite, numerados sem buraco (`AC-1`, `AC-2`, ...), sob o título «Acceptance criteria».
- **O que fica para outras issues.**

## A issue de plano

Antes de construir, o trabalho ganha um plano, e o plano vive numa issue própria.

| Regra | O que diz |
|---|---|
| Uma issue de plano | O plano é uma issue do formulário `Plan`, sub-issue da issue que ele resolve (a user story, o bug, a tech task ou a initiative). |
| O conteúdo | O formulário pede a issue mãe, por que, o que entra, como, quantos PRs se espera, os critérios de aceite e o que fica para outras issues. |
| A aprovação | Uma pessoa aprova o plano na própria issue. Sem a aprovação, a agência não começa. |
| Decisões tomadas | O plano chega com as decisões tomadas e a base de cada uma. Uma pergunta que ninguém decidiu vira um spike, e não um plano. |
| Mudança de rumo | Um plano que muda depois de aprovado volta para aprovação, com a mudança escrita na issue. |
| A execução | Os PRs citam a issue de plano. Ela fecha quando os PRs dela entram; a issue mãe fecha quando todos os planos fecham. |

## Os issue forms

Os formulários de issue são os do [Ahrena Framework](https://github.com/ahrenatechnology/ahrena-framework), como estão no framework:

| Formulário | Para quê |
|---|---|
| Initiative | Um objetivo grande, que se divide em epics. Numa organização, cada projeto tem a sua, e um incremento entra nela ou numa milestone dela |
| Epic | Uma entrega que se divide em histórias e tarefas |
| User story for API | Um comportamento novo de API, com os cenários em Given/When/Then |
| User story for frontend | Um comportamento novo de tela, com os cenários em Given/When/Then |
| User story for CLI | Um comportamento novo de linha de comando, com os cenários em Given/When/Then |
| Tech task | Trabalho técnico sem comportamento novo para quem usa |
| Bug | Algo que não se comporta como deveria |
| Spike | Uma pergunta a responder antes de decidir |
| Plan | O plano executável de uma issue mãe, aprovado antes de construir |

O repositório `.github` publica esses formulários como padrão da organização: um repositório que não tem `.github/ISSUE_TEMPLATE/` próprio usa estes. Eles ficam em inglês, como no framework, para não virarem uma cópia que fica para trás. É a exceção escrita à regra de [pt-BR na tela](/how-we-work/language).

O tipo da issue é o Issue Type nativo do GitHub, e não um label. A organização de origem de um item vai no label `org:<slug>`.

## Rastreabilidade

Cada critério de aceite tem um teste que o nomeia, com o token `#<issue>/AC-<n>`. O check `traceability`, dentro do `ci`, confere os dois sentidos no pull request:

1. toda issue que o PR fecha lista os critérios, numerados sem buraco;
2. todo critério vivo dessas issues é nomeado por um teste;
3. todo critério que um teste alterado nomeia existe.

Um PR que não fecha issue não tem o que rastrear, e o check fica verde.
