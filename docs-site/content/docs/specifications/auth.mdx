## Quem emite o token

| Quem usa | Identity Manager | Identidade |
|---|---|---|
| A organização, nas instalações dela | O Identity Manager da instalação, no realm `main`: `https://<endereço da instalação>/auth/realms/main` | As pessoas que a organização convida, ou o emissor OIDC da organização, federado |
| O time da Barte, no Backstage e nos serviços internos | Um Identity Manager próprio, no control plane, separado dos das instalações | O Google Workspace da Barte, federado, só para contas do domínio da Barte |

- **O Identity Manager é o único login.** Nenhum componente tem tela de login, servidor de autorização ou conta local própria. Nada de login se constrói no repositório de um componente.
- **Não existe acesso anônimo.** Toda chamada a uma rota protegida tem uma pessoa ou uma conta de serviço autenticada.

## Toda API e todo MCP é um recurso protegido

- **Cada API e cada MCP valida o token sozinho**: o emissor, a audiência, a assinatura e a validade. No control plane, ele confere também o domínio da conta. Não há proxy de autenticação na frente de um MCP.
- **Ele publica os metadados de recurso protegido** da [RFC 9728](https://www.rfc-editor.org/rfc/rfc9728), apontando para o Identity Manager. É por eles que um client MCP descobre onde fazer login.
- **Um pedido sem token, ou com token de outro emissor ou de outra audiência, é `401`**, com `WWW-Authenticate: Bearer resource_metadata=<endereço dos metadados>` e o code `unauthorized` ([catálogo](/specifications/errors/catalog)).
- **A audiência é o endereço do recurso** ([RFC 8707](https://www.rfc-editor.org/rfc/rfc8707)). O token de um front-end leva a audiência `<origem>/api` e não abre o `/mcp`, mesmo que traga `mcp` no escopo: quem decide é a audiência.
- **Um MCP que chama uma API troca o token** pelo da API, por [token exchange](https://www.rfc-editor.org/rfc/rfc8693) (RFC 8693). Ele não repassa o token que recebeu.
- **Nenhuma API abre CORS.** O navegador nunca chama a API direto.

## Front-ends

- **O front-end é um client público.** Ele se registra no Identity Manager por registro dinâmico de client (DCR), sem segredo, com `token_endpoint_auth_method: none`.
- **O login é o authorization code com PKCE S256.** Sem PKCE, o Identity Manager não emite código.
- **O token fica no servidor do front-end (BFF).** O BFF recebe o código, troca pelo token e chama a API. O navegador só recebe o cookie de sessão do próprio front-end.
- **O access token vale 5 minutos.** O BFF renova pelo `refresh_token`, sem nova tela de login, enquanto a sessão da pessoa vale. Quando a renovação volta `invalid_grant`, a sessão acabou, e a pessoa vai ao login de novo.

## Clients MCP

- **Um client MCP se registra por DCR no Identity Manager**, com a política de registro do Identity Manager e um escopo com a audiência do MCP.
- **Uma ponte local**, que roda na máquina da pessoa, usa um client público fixo com device code. A política do registro dinâmico não aceita device code, e por isso a ponte não se registra sozinha.

## Contas de serviço

**Um processo sem pessoa usa `client_credentials`**, com uma conta de serviço própria no Identity Manager. A conta tem só o papel de que o processo precisa.

## Papéis

Os papéis são os do realm do Identity Manager, e ele é a fonte deles:

| Papel | De quem | O que é |
|---|---|---|
| `owner` | Organização | A pessoa dona da conta. Tem todos os poderes dentro dela, a administração de pessoas inclusive |
| `admin` | Organização | Administra pessoas do próprio nível para baixo |
| `approver` | Organização | Decide as [aprovações](/specifications/approvals) |
| `analyst` | Organização | Opera e consulta |
| `viewer` | Organização | Só consulta |
| `operator` | Plataforma | O papel da Barte que opera a plataforma. Administra pessoas do próprio nível para baixo, fica fora da linha da organização e nunca decide aprovação |
| `root` | Plataforma | A conta da Barte que nasce com a instalação. Só administra pessoas e nunca alcança dado: uma rota de dado responde `403` ao `root` |

Ninguém administra quem está acima, nem dá privilégio acima do próprio nível. Cada rota declara os papéis que a abrem. As rotas do contrato da plataforma usam a escada `owner > operator > analyst`, em que quem tem um papel tem o que os de baixo têm.

- **Quem decide o acesso é a API, e não a tela.** `GET /me` devolve os papéis da pessoa para o front-end mostrar ou esconder telas, mas a API confere o papel em toda rota.
- **O papel decide também o que a pessoa vê dentro da rota.** Um campo sensível só sai inteiro para quem a instalação declara. Para os outros, ele sai mascarado, e o valor nunca chega ao navegador.
- **Uma pessoa sem o papel recebe `403`** com o code `forbidden`.
- **Os papéis de módulo que o contrato traz em `x-barte-roles` saem do contrato.**
