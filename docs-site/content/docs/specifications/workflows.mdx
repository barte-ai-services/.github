## O Workflow Manager orquestra tudo

**O Workflow Manager (o Loom, sobre o Temporal) é o único orquestrador da plataforma.** Processo durável, processo de carga alta e todo outro fluxo de trabalho passam por ele: o deploy, a promoção, a criação de uma organização, o laço de um agente, a tarefa periódica.

- **Nada mais orquestra**: nem Step Functions, nem EventBridge Scheduler, nem Lambda em cron, nem GitHub Actions como esteira de deploy ou de apply. Uma tarefa periódica é um schedule do Workflow Manager.
- **O Airflow só existe dentro do Data Operator**, para o paralelismo de um pipeline de dados. Ele não orquestra nada fora do pipeline.
- **O laço de um agente é um workflow**, e não um checkpointer de framework de agente. Um motor de durabilidade só.

## O codec

- **Todo processo que grava ou lê payload no Temporal usa o codec do Loom**: o pacote `loom-codec` (`loom/packages/codec`), importado como `loom_codec`. O worker usa, e a API também, quando inicia ou sinaliza um workflow.
- **O histórico é cifrado.** O codec cifra o payload com AES-GCM, com uma chave de dados do KMS, e desvia para o S3 o que passa de 128 KB.
- **Nada que desligue o codec entra no compose nem no deploy.** Sem o codec, a API não inicia workflow em claro.

## A fila

- **A task queue de um projeto é o id do projeto.** O worker e a API do projeto levam o mesmo id.
- **O trabalho da plataforma**, que não é de nenhum projeto, usa o slug do componente como fila.

## Um worker por domínio

**Um domínio de fluxo é um worker.** Um domínio novo é uma pasta nova em `workers/`, e não um workflow a mais no worker de outro domínio.

## O código do workflow é determinístico

O Temporal re-executa o workflow do zero na recuperação, sobre o histórico gravado. Por isso:

- **Nada de relógio, acaso, rede, ambiente ou chamada de modelo no código do workflow.** Hora, número aleatório e leitura de banco vêm do SDK ou de uma atividade.
- **A inferência é uma atividade própria**, separada da atividade com efeito colateral. As duas falham por motivos diferentes e têm `RetryPolicy` diferentes. No replay, o resultado do modelo é lido do histórico, e não gerado de novo.
- **`model_id` e `prompt_version` são argumentos do workflow**, e nunca vêm do ambiente. Ficam gravados, e dá para responder depois qual modelo e qual prompt tomaram a decisão.
- **Mudar um workflow que já tem execução em voo quebra o replay dela**: o Temporal re-executa o código novo sobre o histórico gravado pelo antigo.

## As atividades

- **Toda atividade declara `start_to_close_timeout` e uma `RetryPolicy`.** Não há atividade com o timeout do padrão.
- **Um efeito colateral que não é idempotente roda com `maximum_attempts=1`.**
- **Só a atividade abre conexão.** Banco é rede, e o código do workflow não faz rede.

```python
result = await workflow.execute_activity(
    classify_invoice,
    ClassifyInput(invoice_id=invoice_id, model_id=model_id, prompt_version=prompt_version),
    start_to_close_timeout=timedelta(minutes=2),
    retry_policy=RetryPolicy(maximum_attempts=3),
)
```
