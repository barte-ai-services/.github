## O formato

Todo erro das APIs sai em `application/problem+json`, no formato da [RFC 9457](https://www.rfc-editor.org/rfc/rfc9457):

```json
{
  "type": "https://barte.ai/problems/422",
  "title": "Campo recusado.",
  "status": 422,
  "detail": "A medida receita_bruta não existe nesta visão.",
  "instance": "6f1c2a9e-3b7d-4c51-9a0e-2f8d4b6c1e73",
  "code": "refused",
  "errors": [
    { "field": "measures[0]", "message": "A medida receita_bruta não existe nesta visão." }
  ]
}
```

| Campo | Sempre | O que é |
|---|---|---|
| `type` | sim | `https://barte.ai/problems/{status}`, um URI estável por status |
| `title` | sim | A mensagem do catálogo, em pt-BR |
| `status` | sim | O status HTTP, igual ao da resposta |
| `detail` | não | O que aconteceu neste pedido, em pt-BR. Nunca traz segredo, dado pessoal ou o corpo de um provedor |
| `instance` | sim | O id da requisição, igual ao `X-Request-Id` da resposta |
| `code` | sim, desde o contrato 1.1.0 | O código do erro, em snake_case, do [catálogo](/specifications/errors/catalog) |
| `errors` | num `422` de campo | A lista `[{field, message}]` dos campos recusados |

- **Quem consome trata pelo `code`**, e nunca pelo texto de `title` ou `detail`.
- **O `code` entra no contrato na versão 1.1.0.** Até lá, o `type` por status e o `title` do contrato identificam o erro.
- **Um `code` novo entra primeiro no catálogo**, com status, mensagem e quando acontece. Um componente não inventa código.
- **Um `500` não diz o porquê.** O `title` é «Erro interno.», e o detalhe fica no log, achado pelo `instance`.

## O mesmo erro na REST e no MCP

**O status da REST e a recusa do MCP saem da mesma classe de exceção.** A exceção de domínio declara o `code` e o status. A REST a responde como problem+json, e a ferramenta do MCP a devolve como recusa, com o mesmo texto.

Uma ferramenta do MCP que recusa devolve `isError: true`, com o texto:

```text
<code>: <mensagem em pt-BR>
```

- Quando a recusa tem opções válidas, o texto as lista: as medidas da visão, os provedores da instalação.
- Quando um valor está perto de um válido, o texto traz a dica «você quis dizer …?».
- O agente lê esse texto e corrige sozinho. Por isso ele diz o que está errado e o que vale, e não só que falhou.

```text
refused: a medida receita_bruta não existe nesta visão. Medidas: receita, ticket_medio, quantidade. Você quis dizer receita?
```

## Onde o formato é outro

- **Os endpoints OAuth** do Identity Manager (token, autorização, registro dinâmico de client) seguem o formato de erro das [RFC 6749](https://www.rfc-editor.org/rfc/rfc6749#section-5.2), [RFC 7591](https://www.rfc-editor.org/rfc/rfc7591#section-3.2.2) e [RFC 6750](https://www.rfc-editor.org/rfc/rfc6750#section-3.1): `{"error": "invalid_grant", "error_description": "…"}`. Quem integra com OAuth espera esse formato.
- **O Integration Gateway** ainda responde `{error, request_id}`. Ele migra para problem+json, com o `code` igual à string antiga de `error` e o `instance` igual ao `request_id`.
