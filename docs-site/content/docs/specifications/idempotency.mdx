## Na API: `Idempotency-Key`

Uma ação é um `POST` que muda estado: pausar, retomar, coletar, reconstruir, testar uma conexão ([APIs](/specifications/apis)). Toda rota de ação segue estas regras:

| Regra | Valor |
|---|---|
| O cabeçalho | `Idempotency-Key`, obrigatório em toda rota de ação |
| O tamanho | De 1 a 128 caracteres. Fora disso, `400` com `invalid_idempotency_key` |
| A janela | 24 horas desde o primeiro pedido |
| O alcance | Por pessoa: a chave vale para quem chamou, o método e a rota. A mesma chave de outra pessoa é outro pedido |
| A repetição | A mesma chave com o mesmo corpo devolve a mesma resposta, com `Idempotent-Replayed: true`, e a ação não roda de novo |
| O conflito | A mesma chave com outro corpo é `422` com `idempotency_key_reused` |

```http
POST /api/v1/data-operator/providers/{provider}/pause
Authorization: Bearer …
Idempotency-Key: pause-2026-11-02-a1
```

- **Quem chama gera a chave**, uma por intenção, e a repete em toda nova tentativa da mesma intenção. Uma intenção nova pede uma chave nova.
- **Repetir com a chave é sempre seguro**: depois de um timeout, de um `502` ou de uma queda de conexão.
- **Uma leitura não leva chave.** `GET` e `POST …/query` não mudam estado.

## No consumidor: a chave e o workflow

Trabalho assíncrono entre componentes é um workflow do Workflow Manager ([eventos](/specifications/events), [workflows](/specifications/workflows)). Repetir o pedido não pode dar dois efeitos:

- **O id do workflow é único.** O Temporal não aceita dois workflows em andamento com o mesmo id. Quem inicia um workflow a partir de uma ação deriva o id da intenção, como a `Idempotency-Key` do pedido, e a repetição encontra o workflow que já existe.
- **A atividade com efeito colateral que não é idempotente** roda com `maximum_attempts=1` na `RetryPolicy`, e não repete sozinha.
