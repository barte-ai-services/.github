Esta página vale para qualquer contribuição a um repositório da `barte-ai-services`. O caminho completo de uma mudança, do plano ao merge, está em [Como trabalhamos](/how-we-work).

## Issue primeiro

- **Nenhuma mudança começa sem uma issue**, nem as pequenas. A issue carrega os critérios de aceite `AC-n`, e cada critério tem um teste ([issues](/how-we-work/issues)).
- **Trabalho grande começa num plano**, aprovado numa issue de plano antes de construir. O plano diz as peças, a ordem e as decisões.
- **Trabalhamos em branches no próprio repositório**, sem forks.

## Branch

A branch segue `<type>/<issue>-<slug>`:

- `<type>` é um dos tipos de commit abaixo;
- `<issue>` é o número da issue;
- `<slug>` é um resumo curto em inglês, kebab-case.

```text
feat/42-token-refresh
fix/57-empty-cursor
```

## Commits pequenos

- **Um commit por mudança lógica.** Não misture o que não se relaciona.
- **Cada commit funciona sozinho**: compila e passa nos testes sempre que possível.
- **Se ficou grande, divida.** Uma issue grande vira uma pilha de PRs ([pull requests](/how-we-work/pull-requests)).

## Conventional Commits, em inglês

Toda mensagem de commit e todo título de PR seguem [Conventional Commits](https://www.conventionalcommits.org/en/v1.0.0/) e são escritos **em inglês**.

```text
<type>(<optional scope>): <subject>

<optional body>

<optional footer>
```

| Tipo | Quando |
| --- | --- |
| `feat` | Funcionalidade nova |
| `fix` | Correção de bug |
| `docs` | Só documentação |
| `style` | Formatação, sem mudança de comportamento |
| `refactor` | Mudança de código que não corrige bug nem cria funcionalidade |
| `perf` | Desempenho |
| `test` | Testes novos ou corrigidos |
| `build` | Build ou dependências |
| `ci` | Integração contínua |
| `chore` | Manutenção que não cabe nos outros tipos |
| `revert` | Reversão de um commit anterior |

O cabeçalho:

- tem **no máximo 100 caracteres**;
- tem assunto que **começa em minúscula** e **não termina com ponto**;
- leva o escopo, quando há, entre parênteses: `feat(auth): add token refresh`;
- marca uma quebra de compatibilidade com `!` depois do tipo ou do escopo, ou com o rodapé `BREAKING CHANGE:`.

```text
feat(auth): refresh the access token before it expires

Retry the request once when the server answers 401.

Closes #42
```

## O título do PR é o commit

A `main` só aceita **squash**. O título do PR vira o cabeçalho do commit na `main`, então é ele que mais importa: escreva-o como um commit.

O workflow `conventional-pr` confere o PR em duas partes:

| Parte | O que confere |
| --- | --- |
| Título | O tipo é um dos onze da tabela, e o assunto começa em minúscula e não termina com ponto |
| Commits | Cada commit do PR, pelo commitlint, com o `commitlint.config.js` do repositório: o tipo, o cabeçalho até 100 caracteres, o assunto não vazio e sem ponto final |

Neste repositório, ele roda em modo de aviso: aponta o erro no PR e não bloqueia o merge. O único check obrigatório é o `ci` ([pull requests](/how-we-work/pull-requests)). O limite de 100 caracteres do título não é conferido pelo check; vale do mesmo jeito.

## Assinatura

O commit que entra na `main` é o squash feito pelo GitHub, e o GitHub o assina: ele aparece como **Verified**. Isso basta. Não é preciso configurar assinatura GPG ou SSH na sua máquina.

## Idioma

**Bastidores em inglês, pt-BR na tela** ([idioma](/how-we-work/language)):

- **Em inglês:** código, identificadores, nomes de arquivo e de pasta, rotas, chaves de JSON, tabelas e colunas, variáveis de ambiente, nomes de teste, nomes de branch e mensagens de commit.
- **Em pt-BR:** o que a pessoa vê na tela, a documentação deste handbook, as issues e o corpo dos PRs.
